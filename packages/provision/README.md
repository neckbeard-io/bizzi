# @bizzi/provision

ADE provisioning for bizzi (spec §7, tech-choices D6): detect the coding agents on a machine, install, update or uninstall them from declarative recipes, and help with logins on headless machines.

## API

```ts
import {
  probe, probeAll, probeTool,          // detection → AgentProbe (never throws)
  latestVersion, clearLatestVersionCache, compareVersions,
  planInstall, runPlan,                 // install / update / uninstall
  detectLoginPrompts, LoginPromptScanner, localhostCallbackPort, loginSpec, stripAnsi,
  loadRecipes, defaultRecipes, parseRecipe, validateRecipe, RecipeSet, RecipeError, BUILTIN_RECIPES_DIR,
  augmentedPath, augmentedEnv, extraPathDirs, findBinary, resolveNpmPrefix, homeDir, toolsDir,
  currentPlatform, parsePlatform, platformKey, execCapture,
  satisfies, parseRange, assessSupport,  // supported-version ranges
  resolveExecutable, assessInstall, installFacts, preferredMethod, watchPaths, methodBinDir,
} from '@bizzi/provision';
```

- **`resolveExecutable(path, { searchDirs, home, stopAt })`** follows symlinks and wrapper shims to the binary that actually runs. A POSIX shell script with `exec` lines is a shim: a literal (or `$HOME`/literal-variable) exec target is followed; `exec <same name>` and wrappers whose targets can't be read hand over to the next executable with that name on `searchDirs` (e.g. a terminal app's `claude` shim → its wrapper → `~/.local/bin/claude` → `~/.local/share/claude/versions/<v>`). Scripts without `exec`, and node/python scripts, are final.
- **`assessInstall(recipe, { path, version }, opts)`** returns the real path, the method whose `pathHints` match it, the recipe's `preferredMethod` (first method for the platform), `support` / `supportReason` / `remedies`, the install's facts (`brewFormula` from `Cellar/<formula>` plus `INSTALL_RECEIPT.json`'s tap, `brewCask` from `Caskroom/<cask>`, `npmPrefix`) and the paths to watch for updates. `probe()` reports all of these.
- **Supported versions:** a recipe's `support` block declares `versions` (outside → `unsupported`, with the recipe's reason and remedies) and the adapter's `tested` range (outside → `untested`). Ranges are `>=`, `>`, `<=`, `<`, `=` comparators, space = AND, `||` = OR. `support.migrate` lists methods that update worse than the preferred one (Claude: `brew`, `npm`); such installs get a `migrate` remedy.
- **Adopted installs:** `planInstall(..., { action: 'update' | 'uninstall', installedPath })` fills `{{brewFormula}}`, `{{brewCask}}` and `{{npmPrefix}}` from the install's real path, so an OpenCode install from Homebrew core's `opencode` formula is upgraded and uninstalled as `opencode`, not as `anomalyco/tap/opencode-v2`.

- **`probe(agent, env?, opts?)`** returns an `AgentProbe` (protocol `model.ts`). It searches an augmented PATH: the inherited PATH, then `~/.local/bin`, `/opt/homebrew/bin` (on macOS), `/usr/local/bin`, the npm global bin, `~/.bizzi/tools/*/bin`, then the recipe's search paths. That way it finds per-user installs even under launchd, systemd or a container entrypoint. It tries each candidate binary until one prints a version, so broken shims and wrappers are skipped. It then runs the recipe's auth status command, but only commands marked `sideEffectFree`. If that command can't run, it falls back to env/file heuristics. Every child process has a timeout. `opts.latest`: `'cached'` (the default) only reads the cache, `true` fetches, and `false` skips the check.
- **`latestVersion(name, opts?)`** tries the recipe's `latest` sources in order (vendor URL, GitHub releases, npm registry, Node dist index). Results are cached per recipe and platform for 1 hour and failures for 6 minutes. Concurrent calls share one request. It never throws.
- **`planInstall(name, platform?, methodOrOptions?)`** returns an `InstallPlan`: the ordered steps, the `extraPath` to prepend, the target dir and any warnings. Options: `method`, `action` (`install`, `update` or `uninstall`), `version`, `forAgent`, `hasCommand`, `verify`. Without a `method`, it picks the first method for the platform whose `requires` are on PATH. When a requirement is missing but a tool recipe provides it (for example `npm` from `node`), the plan installs that tool first into `~/.bizzi/tools`. Versions are validated, and template values are shell-quoted when they contain unsafe characters. Install and update plans end with a `<binary> --version` verify step.
- **`runPlan(plan, { dryRun, onProgress, env, cwd, allowSudo, signal })`** runs each step in a PTY-less child process. stdin is `/dev/null`, so installer prompts get EOF. Each child has its own process group, so a timeout or abort kills the whole `curl | sh` tree. The PATH is augmented plus `plan.extraPath`, and per-step env and cwd apply. Progress events have exactly the shape of the protocol's `install.progress` data: `{ agent, stage, message?, done?, ok? }`. The stages are `plan`, `warning`, `step` (description plus `$ command`), `output` (one event per line) and `done`. `dryRun` prints the commands and runs nothing. Plans with `requiresSudo` steps are refused unless `allowSudo` is set.
- **`detectLoginPrompts(chunk, { cols? })`** returns `{ urls, codes, awaitingCodeInput, text }` from terminal output. It handles ANSI CSI and OSC sequences, OSC 8 hyperlinks (target plus label), `\r` redraws, and URLs soft-wrapped at the terminal width or indented inside TUI boxes. It also trims trailing punctuation and unbalanced brackets. Codes come from `XXXX-XXXX`-style tokens near "code" and from `user_code` URL params. Every URL carries `callbackPort` when its OAuth flow redirects to localhost. `LoginPromptScanner` is the streaming version: it buffers across chunks, holds back a URL that is still being written, and reports each URL and code once.
- **`localhostCallbackPort(url)`** returns the localhost port that must be forwarded through the hub during a remote login. That is either the URL's own port, when the URL is on localhost, or the port in its `redirect_uri`/`redirect_url`/`callback` parameter.

## Recipes

Recipes are data. Each one is a YAML file in `recipes/<name>.yaml`, validated at load time against the TypeScript schema in `src/schema.ts`. Validation is structural (unknown keys are errors) and semantic: regexes must compile, template variables must exist on every platform a method supports, every step needs exactly one of `run`/`argv`, method ids must be unique, and tool references must resolve. `loadRecipes([BUILTIN_RECIPES_DIR, overridesDir])` lets a local directory override a shipped recipe, so fixing a recipe doesn't need a bizzi release.

For each agent or tool, per OS × arch (`darwin-arm64`, `linux-x64-musl`, …, with per-platform `vars`), a recipe defines:

- **detect**: binary names, extra search paths, and a version command plus regex.
- **latest**: version sources, in order.
- **support** (agents): supported and tested version ranges, the unsupported reason and remedies, and which methods to offer migration from. An `upgrade` remedy with an `id` and `steps` runs those steps instead of its method's update (`planInstall(…, { remedy: id })`). Its verify step then fails unless the installed version is inside `versions`. Steps never reach the listing.
- **methods**: install methods in preference order. Each has a kind (`script`, `brew`, `npm` or `binary`), platform filters, `requires`, `targetDir`/`binDir`, whether it is `pinnable`, `pathHints` (to tell which method installed a binary), `watch` (paths that change on update; Homebrew and npm package dirs are added automatically), and `install`/`update`/`uninstall` steps. Each step has `run` (sh) or `argv`, plus `requiresSudo`, `env`, `cwd`, `timeoutMs`, `allowFailure` and `when: pinned|unpinned`.
- **login**: the interactive command (run it in a PTY and feed the output through the scanner), plus headless alternatives: an API key env var, a long-lived token command, device code, a secret on stdin, a config file, or copying credentials over.
- **auth**: a status command (`format`, exit codes, JSON fields or regexes, and whether it is side-effect free), heuristic `rules` (env vars, files, JSON field equals), and which state to report when nothing matched.

Templates use `{{var}}` or `{{var|default}}`, so they don't collide with shell `$VAR`. Engine variables are `version`, `home`, `toolsDir`, `toolDir` (`toolsDir/name/version`), `name`, `os`, `arch`, `libc`, `platform` and `brewBin`, plus the platform `vars`. Update/uninstall plans of an adopted install also get `brewFormula`, `brewCask` and `npmPrefix` (steps give them defaults, e.g. `{{brewFormula|anomalyco/tap/opencode-v2}}`). A leading `~/` expands to home in paths and env values.

**No sudo:** every step has `requiresSudo: false`. Everything installs under `$HOME`: `~/.local/bin`, `~/.opencode/bin`, or `~/.bizzi/tools/<name>/<version>` with a `~/.bizzi/tools/<name>/bin` symlink. The exception is Homebrew, which macOS users own anyway. npm installs use `NPM_CONFIG_PREFIX=~/.local`. In the Linux node container (topology §2.2), `$HOME` is the persistent `node-home` volume, so installs and logins survive image upgrades.

## Tests

`npm test -w @bizzi/provision` runs offline. It covers schema validation of every recipe, plus negative cases; plan generation per platform; dry runs of every agent recipe; real runs of a fake recipe that only echoes and writes in a temp dir; PATH augmentation; probing fake binaries (broken shims, timeouts, auth parsing); login prompt detection on samples for each agent; latest-version sources with a fake fetch; and read-only `--version` probes of the agents installed on this machine (claude and opencode, skipped when absent; codex and agy must report `installed: false`). Nothing is ever installed, updated or logged in.
